# Stability guarantee

rstorch 1.0 follows [semantic versioning](https://semver.org). This file states
exactly what that covers, because "1.0" on its own does not.

## What is covered

Everything reachable from `rstorch::` in a build with any combination of the
`typed`, `hub`, `rayon` and `metal` features. A release that removes an item,
narrows a signature, or moves a type out of a module is a **2.0**.

Six recorded surfaces in [`api/`](api/) define this concretely, one per feature
combination CI can build. They are generated by `cargo public-api` and diffed on
every run by [`tools/api-baseline.sh`](tools/api-baseline.sh); a change to any
of them has to be an intentional commit that rewrites the baseline, not a
side effect somebody notices after publishing. `src/prelude.rs` is pinned by
content hash on top of that, because the baselines record what the first-hour
surface contains but not the order a reader meets it in.

Also covered, as ordinary API:

- **Error variants.** `Error` is `#[non_exhaustive]`, so adding a variant is a
  minor release. Removing one, or changing which variant an existing operation
  raises for an existing input, is breaking.
- **The `metal` backend's API.** Its *performance* is not a guarantee — see
  below — but its types and signatures are held to the same bar as the rest.
- **`Grads` linearity.** That `Grads` is neither `Clone` nor droppable without
  a warning is load-bearing, not an implementation detail. The compile-fail
  suite in `tests/linearity_ui.rs` pins it.

## What is not covered

- **`rstorch::testing`**, behind the `testing` feature. It is the
  finite-difference harness the crate tests itself with, and its signature
  follows the crate's own test needs. It is public so downstream code can
  reuse it, not because it is frozen.
- **Numerical output to the last bit.** Kernel changes may move results within
  floating-point tolerance. What is stable is that a given build is
  deterministic: seeded runs reproduce, and the `rayon` feature does not change
  results, because CPU kernels partition by output element and never accumulate
  a float across threads in a racing order.
- **Anything private.** Backends, layouts, storage and dispatch are internal
  and change freely.
- **Benchmark numbers.** The design record they come from is working material
  kept out of the repository; only the recorded surfaces in `api/` are
  normative.

## Feature flags

Features are additive: enabling one never removes or changes an item that was
there without it. `typed` in particular is a wrapper — it adds a namespace, and
does not alter the dynamic API.

## Metal is stable API, not competitive performance

The `metal` backend is correct and conformance-tested against the CPU backend.
It is also, on the workloads recorded in the project's own performance gate,
**slower than the CPU backend** — the tiny-transformer AdamW case by a wide
margin. That is why `Device::best_available` returns CPU and why the backend is
never selected implicitly.

Its API is covered by this guarantee. Its speed is not: closing that gap is
ordinary optimization work that may land in any patch release.

## Minimum supported Rust version

The MSRV is **1.88**, and it is CI-enforced on every run.

Raising it is a **minor** version bump, not a patch. It will be raised only
when a language or standard-library feature is worth it, and it will be
mentioned in the changelog.

## Reporting a break

If a minor or patch release breaks your build, that is a bug — please open an
issue. The recorded surfaces in `api/` make the answer checkable rather than a
matter of memory.
